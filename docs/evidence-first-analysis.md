# Evidence-First Analysis — Engineering Discipline Reference

A small ruleset for QA investigations, status reports, and multi-phase
decisions on this project. Codified after a sequence of analytical
mistakes was caught during the A1–E4 roadmap. The pattern that produced
those mistakes is documented at the bottom (Anti-pattern catalog) with
concrete examples from this codebase, so the rules below are anchored
to real failures rather than abstract principles.

This doc is short by design. If it's not three pages or less, no one
will read it during an investigation.

## 1. Purpose

Avoid the common QA-investigation failure mode where:

```
observation  →  confident interpretation  →  recommendation
                          ↑
                  the "what else could
                  explain this?" step
                  is skipped
```

The remedy is to make the skipped step explicit:

```
observation  →  hypothesis  →  evidence  →  decision
```

Each arrow is a discipline gate. The rules below describe how to walk
each gate without short-cutting it.

## 2. The Six Rules

### Rule 1 — Falsifiability test for "is" claims

Any claim using **"is / confirms / therefore / root cause / proves"**
must be paired with the falsifying observation:

> *What would I expect to see if this claim were false?*

If you can't write that sentence, the claim is still a hypothesis —
mark it as one, or remove it.

**Project example (failed application):**
> "The 41-test result is exactly what we wanted."

Falsification test: *what would 41 tests look like if it WASN'T what
we wanted?* Equally consistent with: skipped tests, duplicate runs,
configuration error. The "is" was unsupported.

**Corrected:** "Test count rose from 3 to 41. This is consistent with
removal of the group filter as the binding constraint, but does not on
its own prove all intended tests executed."

### Rule 2 — Vocabulary calibration

When the evidence is not yet sufficient for an "is" claim, downgrade
to calibrated phrasing:

| Speculative | Calibrated |
|---|---|
| "X is caused by Y" | "X is consistent with Y" |
| "this confirms Y" | "this is consistent with the hypothesis that Y" |
| "therefore Z" | "this would suggest Z, pending …" |
| "root cause is W" | "the most likely contributing factor is W" |
| "this fixes the problem" | "this addresses one of the observed signals; the score model needs to be evaluated to confirm" |

This is not stylistic. The downgrade carries information: it tells
the reader the strength of the evidence.

### Rule 3 — Run the model before quantitative claims

Any claim that involves a number — "this would improve the score by
N," "we'd save M points," "this brings us into band X" — must be
computed against the actual model, not estimated qualitatively.

**Project example (failed application):**
> "The C4 evidence + the rebrand selector cleanup are the two changes
> that would move this back to green."

The score model was in front of me (see `scoring-weights-rationale.md`).
The capped sources (JS errors at 20, fallbacks at 30) make most of the
penalty floor independent of test-failure count. The "back to green"
claim never modeled the actual delta. The right behavior was: open
`scoring-weights-rationale.md`, identify the binding sources, compute
the projected post-fix penalty, then state the result.

**Self-check:** *If I'm using a number, did I derive it from the model
or estimate it?*

### Rule 4 — Derived classifications are inputs, not evidence

This project has classifiers, scorers, and detectors that emit
opinions about data — `FailureClassifier` returns `PRODUCT_BUG`,
`HealthGate` returns `CRITICAL`, the dashboard's largest-Δ-source
attribution points at one column. These outputs are **hypotheses
generated by software**, not facts.

Treat them as the *start* of an investigation, not the end.

**Project example:**
> Two stale-element framework failures were classified as
> `PRODUCT_BUG`. I initially accepted the classification when it
> matched my narrative, then later disputed it when convenient.
> That's inconsistent. Consistent behavior: always treat classifier
> output as input to investigation, regardless of whether it aligns
> with the current hypothesis.

**Self-check:** *Am I citing a classifier output as evidence, or as
the input to verification?*

### Rule 5 — Phased delivery — don't touch production until validation completes

Established pattern from the C4 / B4 work:

| Phase | Scope | Validation gate |
|---|---|---|
| 1 | Abstraction / value types | Stability tests cover canonical + edge cases |
| 2 | Implementation behind sealed interface | Fixture tests cover all branches + invariants |
| 3 | Validation harness / replay / report | Real-data run produces a decision artifact |
| 4 | Production integration behind flag | Decision artifact reviewed; flag default OFF |

Each phase is reversible until the next one starts. When a phase is
declared "frozen" (e.g. C4 fingerprinting / clustering / policy
engine), no refinements are allowed even when tempting — additions
that prepare for the *next* phase (e.g. adding `schemaVersion` to the
archive sidecar in preparation for B4) are explicitly carved out as
exceptions and limited to the absolute minimum.

**Project example:**
> C4 Phase 4 (HealthTracker integration) remains blocked on evidence
> collection. The temptation during Phase 3 was to "just wire it in
> while we're here." Doing so would have contaminated the evidence
> period with a moving target.

**Self-check:** *Does this change cross a phase boundary that hasn't
been unlocked yet? If yes — is the unlock condition explicitly
recorded as met, with the artifact?*

### Rule 6 — Narrow defensible > broad retractable

A narrow claim that turns out to be incomplete costs one follow-up.
A broad claim that turns out to be wrong costs a retraction *and*
the reputational damage of having made the claim.

The cheaper edit is subtraction. Most speculative claims are
additions to an answer that didn't need them.

**Project example:**
> One investigation revision moved from a 6/10 rating to 9/10 mostly
> by *removing* speculative content, not by adding new analysis. The
> ratio of "subtraction-improved" to "addition-improved" is the
> diagnostic: when revision = removal, the original was over-claiming.

**Self-check:** *If I removed every speculative claim, would my
recommendation still hold? If yes — remove them. If no — collect
the evidence first.*

## 3. Application checklists

Three contexts hit these rules most often. The checklists are the
minimum bar for each — apply them inline during the work, not as a
post-hoc audit.

### 3a. Test-failure triage checklist

Before writing a failure-cause statement:

- [ ] Read the failure artifact (`reports/failures/<test>_<timestamp>/`)
  — screenshot, dom.html, console.log, url.txt
- [ ] Confirm the failure type with the artifact, not just the
  classifier label
- [ ] Identify at least one alternative explanation
- [ ] State the cause using Rule 2 vocabulary unless the artifact
  proves it
- [ ] If proposing a fix that touches scoring, run the score impact
  via Rule 3

### 3b. Phase-gate review checklist

Before declaring a phase complete or proposing to start the next phase:

- [ ] State the unlock condition for the next phase in writing
- [ ] Cite the artifact that proves the condition is (or is not) met
- [ ] Confirm no production code outside the current phase was
  touched
- [ ] Confirm tests cover all branches of the new code under all
  relevant flag states
- [ ] State explicitly what the next phase will NOT do (so scope
  creep is visible)

### 3c. Status report checklist

Before publishing a run analysis or status update:

- [ ] No "is / confirms / therefore" without falsification
  observation (Rule 1)
- [ ] No quantitative projection without model computation (Rule 3)
- [ ] No classifier output cited as fact (Rule 4)
- [ ] Section labeled "What is not yet established" listing residual
  uncertainty
- [ ] Recommendations sized to the evidence (don't recommend three
  fixes when only one is supported)

## 4. Anti-pattern catalog

Each anti-pattern below is illustrated with a real instance from
this project's history. The cure is in parentheses.

### A1. "This is exactly what we wanted"
Treats a partial observation (test count rose) as a complete
validation (suite is running correctly). *Cure: state what the
observation confirms and what it does NOT confirm.*

### A2. "Multiple clusters over cap therefore Phase 4 unlocked"
Conclusion derived from cluster headlines in console output rather
than from running the replay harness. *Cure: the replay report is
the decision input, not the console log.*

### A3. "These are framework, those are product"
Classifying failures based on intuition about the code path rather
than on the failure artifacts. *Cure: open the screenshot and DOM
before classifying.*

### A4. "Fix these two things and the score goes green"
Quantitative recommendation made without computing the actual
score delta. *Cure: derive the delta from `HealthPolicy` constants
and the snapshot's contributor breakdown.*

### A5. "Just one small refinement to the frozen layer"
Touching frozen code during an evidence-collection period because
"the change is small." *Cure: schema/test-only additions are allowed
when explicitly carved out; algorithmic changes are not, regardless
of size.*

### A6. "I'll fix the classifier later, the current label is fine"
Accepting a classifier label that matches the current narrative even
after declaring the classifier unreliable in a different context.
*Cure: if the classifier is unreliable for one case, it's unreliable
for all cases until fixed.*

## 6. When to update this doc

Update when:

- A new anti-pattern is observed in practice (add to §4 with the
  specific instance).
- A new context emerges that needs its own checklist (add to §3).
- A rule is found to be either too strict (causing false-positive
  rule violations) or too loose (allowing the failure mode it was
  designed to prevent).

Do NOT update to add abstract principles. Every addition must be
anchored to a specific observed failure or success.
